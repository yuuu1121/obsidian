# 말로 시키면 ROV 여러 대가 알아서 그물을 검사한다 — AquaChat++

> [!abstract] 한 줄 요약
> **"모든 가두리를 검사해줘"** 같은 **자연어 명령**을 GPT-4o가 **JSON 심볼릭 계획**으로 번역하고, ROV 여러 대에 **배터리 잔량과 고장난 추진기 상태를 고려해** 임무를 나눠준다. 아래층에서는 RRT* 경로계획 + 나선형 검사 궤적 + **적응형 추력 재분배**로 추진기가 죽어도 임무를 이어간다. 시뮬레이션(ROS-Gazebo)에서 계획 3종을 비교했고, **사람이 개입하는 HAP**와 **ROV마다 LLM을 다는 MAS**가 중앙집중식(CLP)보다 제약 조건을 훨씬 잘 지켰다.

---

## 0. 이 논문의 위치 — 무엇의 확장인가

`++`가 붙은 이유는 같은 연구실의 선행 연구 **AquaChat**(단일 ROV + LLM)의 확장판이기 때문이다. 무엇이 더해졌는지가 이 논문의 전부라고 봐도 된다.

| 항목 | 기존 (단일 ROV LLM 연구) | **이 논문 (AquaChat++)** |
|---|---|---|
| 로봇 수 | 1대 | **2대 이상 (다중 ROV)** |
| 에너지 | 고려 안 함 | **배터리 인식 임무 배분** |
| 고장 | 고려 안 함 | **추진기 고장 허용 + LLM이 계획 단계에서 미리 반영** |
| 계획 구조 | 단일 LLM | **CLP / HAP / MAS 3종 비교** |
| 재계획 | 없음/제한적 | **이벤트 기반 재계획** (배터리 소진, 고장 발생 시) |

> [!tip] 한 문장 대비
> 선행 연구가 **"LLM으로 ROV 한 대를 말로 조종할 수 있나?"** 였다면, 이 논문은 **"여러 대를, 배터리와 고장이라는 현실 제약 아래서 조율할 수 있나?"** 를 묻는다.

## 1. 문제 — 왜 양식장 그물 검사에 로봇이 필요한가

바다 위 **가두리 양식장(net pen)** 은 거친 파도·조류·생물부착에 계속 노출된다. 그물이 찢어지면 물고기가 탈출하고, 생태계 오염과 금전 손실이 동시에 발생한다. 그래서 **정기 검사가 필수**다.

현재 방식의 한계 세 가지:

**1) 사람이 조종한다.** 대부분 유선(tethered) ROV를 숙련 조종사가 직접 몬다. 느리고, 인건비가 비싸고, 큰 해상 농장으로 **확장이 안 된다**.

**2) 한 대씩 따로 논다.** 여러 대를 띄워도 서로 조율이 안 되고, 미리 짜둔 스크립트대로만 움직인다.

**3) 현실 제약에 대응 못 한다.** 배터리가 떨어져도, 추진기가 하나 고장나도 계획은 그대로다.

> [!question] 그래서 목표는?
> **비전문가가 평범한 말로 지시하면, 여러 대의 ROV가 배터리와 고장 상태를 스스로 따져 임무를 나누고, 도중에 문제가 생기면 다시 계획을 짜게 만들자.**

## 2. 전체 구조 — 2층 아키텍처 (§3.1)

시스템은 **위층(생각)** 과 **아래층(실행)** 으로 딱 나뉜다. 이 분리가 이 논문 설계의 핵심이다.

```
[사용자] "cage-1에 가서 그물 전체를 검사해"
    │
    ├─ 시스템 상태: 가두리 좌표/크기, 도킹스테이션 위치,
    │              각 ROV의 3D 위치·배터리·추진기 상태
    ▼
┌─────────────────────────────────────┐
│  Plan Generation Layer (계획 생성층) │
│  · LLM 기반 플래너 (GPT-4o)          │
│  · 심볼릭 계획(JSON) 생성            │
│  · 검증 모듈: 제약 만족 여부 확인    │
└─────────────────────────────────────┘
    │  move_to(), inspect_net() 같은 심볼릭 액션
    ▼
┌─────────────────────────────────────┐
│  Plan Execution Layer (계획 실행층)  │
│  · RRT* 경로계획 (가두리=원기둥 장애물)│
│  · 나선형(helical) 검사 궤적          │
│  · 적응형 추력 배분 (고장 대응)       │
│  · 캐스케이드 PID 제어기 (4-DOF)      │
└─────────────────────────────────────┘
```

**왜 이렇게 나눴나?** LLM은 "말을 이해하고 순서를 짜는" 일은 잘하지만, 밀리초 단위로 추력을 계산하는 일은 못 한다(그리고 하면 안 된다). 그래서 **기호적 추론(symbolic reasoning)** 과 **물리적 제어(physical control)** 를 갈라놓았다. 모듈성·강건성·실시간 적응이 이 분리에서 나온다.

## 3. 위층 — LLM 플래너 (§3.2)

### 3.1 프롬프트에 뭘 넣나

LLM에게 주는 시스템 프롬프트에는 여섯 가지가 들어간다. **이게 이 논문에서 가장 실용적인 부분**이다.

1. **환경 기하 정보** — 각 원통형 가두리의 모양·지름·깊이·$(x, y)$ 좌표
2. **도킹 스테이션 위치**
3. **각 ROV의 초기 상태** — 3D 위치, 배터리 잔량, 추진기 상태
4. **6×6 추력 배분 행렬** — 이 ROV가 surge/sway/heave/yaw 중 어떤 운동을 할 수 있는지 판단용
5. **시스템 제약과 안전 규칙** — 최소 배터리 임계값, 검사 오프셋 거리, 고장 대응 정책
6. **실행 가능한 함수 목록** — `move_to()`, `inspect_net()` 과 각 인자 설명

> [!note] 핵심 아이디어
> **추력 배분 행렬을 통째로 프롬프트에 넣는다.** LLM이 "추진기 5번이 죽었으니 이 ROV는 heave(수직 운동)를 못 하고, 따라서 깊은 가두리 검사는 배정하면 안 된다"를 **계획 단계에서 미리** 추론하게 만든다. 고장을 사후에 수습하는 게 아니라 계획에 선반영하는 것.

### 3.2 출력은 JSON 심볼릭 계획

"모든 그물을 검사해" → ROV별 순차 계획으로 분해된다. 각 액션은 정확한 인자를 갖는다:

- **좌표** — 어디로 갈지
- **검사 방향** — 위→아래(top-to-bottom) 또는 아래→위
- **오프셋 거리** — 예: 가두리 중심에서 3 m
- **`method` 키워드** — `standard` = 나선 수직 간격 1 m, `detailed` = 0.5 m (더 촘촘한 검사)
- **BatteryStatus** — 실행 후 예상 배터리 잔량
- **ThrusterStatus** — 계획에 반영된 추진기 고장 요약

`method` 파라미터가 영리하다. **자원 사정에 따라 검사 해상도를 LLM이 조절**할 수 있게 만든 손잡이다.

### 3.3 계획 방식 3종 — 이 논문의 실험 축 (§3.2.1~3.2.3)

| 방식 | 구조 | 수식 | 특징 |
|---|---|---|---|
| **CLP** (Central LLM Planner) | 중앙 LLM 1개가 전부 계획 | $P_{\text{initial}} = \text{LLM}(S_t, I_u, C_b, F_t)$ | **원샷(one-shot)**. 가장 빠름 |
| **HAP** (Human-in-the-loop Adaptive Planner) | 계획 → 사람이 보고 피드백 → 재계획 반복 | $P_{\text{final}} = \text{LLM}(P_{\text{initial}}, F_{\text{user}})$ | 가장 정확, **가장 느림** |
| **MAS** (Multi-Agent System) | ROV마다 전용 LLM 에이전트 + 중앙 플래너와 협상 | — | **완전 자율**, 2~4 라운드 |

기호 정리: $S_t$ = 현재 시스템 상태, $I_u$ = 사용자 지시, $C_b$ = 배터리 제약, $F_t$ = 추진기 상태, $F_{\text{user}}$ = 사람 피드백.

MAS는 ROV끼리 직접 통신하지 않고 **중앙 플래너를 거쳐 협상**한다. 저자들이 밝힌 MAS 채택 이유는 단일 에이전트의 두 가지 고질병 때문이다: **긴 호흡 작업에서의 환각(hallucination)**, 그리고 **중간 피드백을 무시하고 처음 계획을 고집하는 경직성**. 매 실행 단계마다 환경 피드백을 받아 경로를 갱신하는 구조로 이를 완화했다.

## 4. 아래층 — 실제로 움직이기 (§3.3)

### 4.1 로봇 모델: BlueROV2

**6자유도 해양 운동방정식**(Fossen 표준):

$$M_{RB}\dot{\nu} + M_A\dot{\nu} + C_{RB}(\nu)\nu + C_A(\nu)\nu + D(\nu)\nu + g(\eta) = \tau_{thrust} + \tau_d$$

각 항의 의미:
- $M_{RB}$, $M_A$ — 강체 질량 + **부가질량**(물속에서 움직이면 주변 물도 같이 밀려 무거워지는 효과)
- $C_{RB}$, $C_A$ — 코리올리·구심력
- $D(\nu)$ — **항력**(선형 + 2차항)
- $g(\eta)$ — 중력·부력 복원력
- $\tau_d$ — 조류 등 외란

자세/속도 벡터는 $\boldsymbol{\eta} = [x,y,z,\phi,\theta,\psi]^T$ (NED 좌표계 위치+자세), $\boldsymbol{\nu} = [u,v,w,p,q,r]^T$ (동체 고정 속도).

주요 파라미터: 질량 11.26 kg, 요 관성 $I_z$ = 0.58 kg·m², heave 부가질량 5.47 kg, heave 선형감쇠 −31.87 N·s/m. UUV Simulator의 검증된 BlueROV2 모델에서 가져왔다.

### 4.2 경로계획: RRT* + 경로 단축

가두리를 **원기둥 장애물**로 모델링하고 3D 공간에서 충돌 없는 경로를 찾는다. RRT*로 트리를 키운 뒤 **후처리로 경로를 짧게 편다** — 경로 위 두 점을 무작위로 뽑아 직선으로 이을 수 있으면 중간 구간을 통째로 대체하는 방식(Algorithm 1).

### 4.3 검사 궤적: 나선(helix)

원통형 그물을 빠짐없이 훑기 위해 나선 궤적을 쓴다:

$$x(t) = x_c + R\cos(\omega t + \theta_0),\quad y(t) = y_c + R\sin(\omega t + \theta_0),\quad z(t) = z_0 + \frac{\Delta z}{2\pi}\omega t$$

여기서 $\omega = 2\pi n_{\text{turns}} / T$, $R$ = 그물 반지름 + 0.5 m (안전 여유), $\Delta z$ = 나선 피치. 반지름과 피치는 **카메라 화각(FoV)에 맞춰** 튜닝한다.

> [!warning] 시뮬레이션 vs 현실 — 저자들이 스스로 짚은 지점
> 시뮬에서는 가두리 중심 좌표를 **정확히 알고 있어서** 3 m 오프셋을 그냥 계산한다. 실제 바다에서는 그 정보가 없거나 부정확하다. 저자들은 실제 배치에서는 **그물 상대 항법(net-relative navigation)** — 카메라·이미징 소나로 그물 표면을 인식해 일정 거리를 유지 — 로 바꿔야 한다고 명시한다. 정직한 서술이지만, **논문에서 검증되지 않은 부분**이라는 뜻이기도 하다.

### 4.4 적응형 추력 배분 — 이 논문의 제어 쪽 핵심

BlueROV2는 추진기 6개로 **4자유도**(surge, sway, heave, yaw)를 제어한다. 원하는 힘 $\tau$와 추진기 명령 $u$의 관계는 $\tau = Ku$.

고장에 대응하기 위해 **제약 최적화**로 푼다:

$$\min_u \|Tu - \tau\|^2 \quad \text{s.t.} \quad u_{min}\cdot d \preceq u \preceq u_{max}\cdot d$$

핵심은 **열화 계수 $d \in [0,1]^6$**:
- $d_i = 0$ (완전 고장) → 해당 추진기 출력이 0으로 **강제 고정**
- $0 < d_i < 1$ (부분 열화) → 유효 추력 한계를 **비례 축소**

단순 유사역행렬($u = T^\dagger\tau$)과 달리, 고장난 추진기를 배분에서 **자동으로 배제**하고 남은 건강한 추진기에 힘을 재분배한다. 복잡한 휴리스틱 규칙 없이 볼록 최적화 한 번으로 처리하는 게 이 방법의 미덕이다.

> [!note] 솔직한 고백
> 저자들은 **시뮬레이터에서 추력 손실을 직접 주입**했다고 명시한다. 즉 **고장 탐지(FDI)는 구현하지 않았다.** 실제로는 모델 기반 추정(명령 추력 vs IMU/DVL 측정 응답 비교), 전기 피드백(모터 전류·전압·RPM), 칼만 필터류 관측기, 과구동 구조의 추진기 간 교차 검증 등이 필요하다고 **방향만 제시**한다.

### 4.5 제어기: 캐스케이드 PID

$$u(t) = K_p e(t) + K_i \int_0^t e(\tau)d\tau + K_d\frac{de(t)}{dt}$$

오차 벡터는 $\mathbf{e}(t) = [e_x, e_y, e_z, e_\psi]^T$. 자유도별로 게인을 따로 튜닝했다. 선택 이유는 "**단순함과 수중 로봇에서의 광범위한 사용 실적**" — 즉 이 논문의 기여점은 제어기가 아니다.

## 5. 실험 설정 (§4)

| 항목 | 내용 |
|---|---|
| 시뮬레이터 | ROS-Gazebo + **UUV Simulator** + BlueROV2 Simulator |
| 그물 모델 | Blender 제작 구형 메시 그물 + 원통 기둥, URDF로 Gazebo 통합 |

| 반복 | 프롬프트당 **20회 실행** |

도킹은 **좌표 도달로 추상화**했다. 실제로는 시각·음향 유도, 기계적 결착, 충전·데이터 인터페이스가 필요하다고 저자들이 명시.

| 5 | ROV1→Cage1–3 후 도킹, ROV2→나머지 | 85 % / 3.5 s | 100 % / 50.3 s | 100 % / 12.5 s |

> [!important] 이 표에서 읽어야 할 것
> **Case 3, 4에서 CLP가 0 %로 완전히 무너진다.** 단순 배정(Case 2, 5)에서는 90 % 근처로 멀쩡하다가, **배터리 제약이나 고장 조건이 붙는 순간 전멸**한다. 원샷 LLM은 "제약을 만족하는 계획을 짜는" 일을 못 한다는 뜻이다. 반복 루프(HAP) 또는 분산 협상(MAS)이 있어야 제약이 지켜진다.
>
> 시간 대비 성능은 **MAS의 압승**이다. HAP 대비 **5~7배 빠르면서** 성공률은 거의 같고, **사람 개입이 전혀 없다**.
>
> 그리고: **계획이 유효하기만 하면 실행 성공률은 항상 100 %**다. 즉 이 시스템의 병목은 전적으로 **계획 층**에 있다.

### 6.2 시나리오별 계획 유효성

| 시나리오 | 조건 | CLP | HAP | MAS |
|---|---|:---:|:---:|:---:|
| **S1** | 배터리 부족 (가두리당 25 % 소모, 중간 도킹 필수) | ❌ | ✅ | ✅ |
| **S2** | 배터리 충분 (마지막에만 도킹) | ✅ | ✅ | ✅ |
| **S3** | 부분 추진기 고장 (검사는 가능, 이후 수리 도킹 필요) | ✅ | ✅ | ✅ |
| **S4** | 치명적 추진기 고장 (제어 불가 → 검사 생략, 즉시 도킹) | ❌ | ✅ | ✅ |

CLP의 실패 방식이 구체적이다. **S1에서는 필요한 도킹 액션을 아예 빼먹었고**, **S4에서는 추진기가 부족한데도 검사를 배정했다.** 둘 다 "제약을 인지하지 못한" 게 아니라 **인지하고도 계획에 반영하지 못한** 실패다.

### 6.3 추진기 고장별 추종 오차 — 이 논문에서 가장 흥미로운 결과

추진기 2·4번은 surge/sway/yaw를, 5번은 heave를 담당한다. 무작위가 아니라 **기여도를 보고 골라서** 껐다.

| 조건 | X (m) | Y (m) | Z (m) | **Yaw (rad)** |
|---|---|---|---|---|
| Normal (정상) | 0.118 | 0.118 | 0.077 | 0.155 |
| F2 (1개 고장) | 0.118 | 0.118 | 0.078 | 0.156 |
| F2,5 (2개 고장) | 0.120 | 0.119 | 0.081 | 0.156 |
| **F2,4,5 (3개 고장)** | 0.110 | 0.110 | 0.081 | **1.011** |

> [!danger] 논문의 결론을 스스로 뒤집는 숫자
> **위치 오차는 3개가 고장나도 12 cm 이하로 멀쩡하다.** 그런데 **yaw 오차만 0.155 → 1.011 rad (약 58°) 로 6.5배 폭증**한다.
>
> 왜 이게 치명적인가? **카메라가 전방을 향해 달려 있기 때문**이다. 요가 58° 틀어지면 카메라가 그물을 못 본다. **위치는 맞는데 검사는 실패**하는 것이다.
>
> 저자들도 이를 인정한다: *"극한 추진기 고장 하에서 시스템 운용을 제한한다."* 즉 F2,4,5 상황에서 이 시스템이 할 수 있는 건 **도킹 스테이션까지 살아 돌아가는 것뿐**이고, 검사는 불가능하다.

### 6.4 통합 실행 예시 (Fig. 12~15)

MAS가 생성한 계획으로 2대가 동시 운용:
- **ROV1 (정상)** — cage_5 → cage_4 → cage_1 검사 → docking_station_1
- **ROV2 (추진기 2·5번 비활성)** — cage_2 → cage_3 검사 → docking_station_2

MAS는 **ROV2의 남은 추진기로도 4자유도가 확보된다고 판단해 검사를 배정**했다. 추력 프로파일에서 추진기 2·5번은 임무 내내 0을 유지하고, 나머지가 보상 증가한다(예: heave 담당 5번이 죽자 6번이 출력을 올려 깊이 유지). ROV2의 roll·pitch는 작고 유계로 유지 — 검사 영상 품질에 중요한 조건이다.

$t$ = 0, 600, 1400, 2000 s의 과도응답 스파이크는 검사 지점 간 `move_to` 기동(가속·재정렬) 때문이고, 그 사이 구간이 실제 검사 구간이다.

## 7. 비판적 평가

### 7.1 강점

**제약을 계획 단계에 밀어 넣은 설계.** 추력 배분 행렬을 프롬프트에 넣어 LLM이 "이 로봇은 heave를 못 한다"를 사전에 추론하게 한 건, 고장을 사후 수습하는 일반적 접근보다 한 단계 앞선다.

**MAS가 실용적 최적점이라는 실증.** HAP 대비 5~7배 빠르고 사람이 필요 없으면서 성능은 대등하다. "LLM 다중 에이전트가 실제로 값을 하는가"에 대한 구체적 수치를 제공한다.

**한계를 숨기지 않는다.** 그물 상대 항법, 고장 탐지 미구현, 도킹 추상화, 외부 베이스라인 부재 — 모두 저자들이 본문에서 스스로 명시했다. 리뷰어 지적을 반영한 흔적이 뚜렷하다.

### 7.2 약점

**외부 베이스라인이 없다.** 저자들도 인정하듯 **CLP/HAP/MAS 사이의 내부 비교(intra-framework)** 뿐이다. 규칙 기반 다중 ROV 플래너나 기존 사전 스크립트 방식과 비교하지 않아서, **"LLM을 써서 좋아졌다"를 증명하지 못한다.** CLP가 무너진 것은 LLM 자체의 한계일 수도 있는데, 그 대안으로 제시된 게 다시 LLM(HAP/MAS)이다. 단순한 제약 만족 문제 해결기(CSP solver)나 MILP가 Case 3·4를 100 %로 풀 가능성이 크다 — **이 비교가 빠진 것이 가장 큰 구멍**이다.

**전부 시뮬레이션.** 실해역 시험이 없다. 그물 상대 항법, 음향 통신 지연, 생물부착으로 인한 시야 저하, 조류 외란 등 현실의 어려움이 전혀 검증되지 않았다.

**제어기가 약하다.** 캐스케이드 PID는 저자들 스스로 "$x$, $y$ 방향 진동 편차"를 결론에서 문제로 지적한다. 병진-회전 동역학 커플링 때문이라며 피드포워드 항 추가를 향후 과제로 남겼다. **F2,4,5에서 yaw가 무너지는 것도 근본적으로는 추력 배분 최적화가 4자유도를 동등 가중치로 다루기 때문**이다 — 검사 임무에서는 yaw에 가중치를 더 줬어야 한다(저자들도 "가중 추력 배분"을 향후 과제로 언급).

**LLM 신뢰성 문제가 남아 있다.** MAS조차 Case 4에서 80 %다. 즉 **5번 중 1번은 잘못된 계획을 만든다.** 검증 모듈이 이를 걸러낸다지만, 실제 해상 작업에서 20 % 계획 실패율은 받아들이기 어렵다. GPT-4o라는 **외부 API 의존**도 수중 환경(통신 제약)에서는 구조적 문제다.

**확장성이 주장에 그친다.** "가두리 5개 고정 배치로 실험했지만 프레임워크는 일반화된다"고 반복하지만, **가두리 20개·ROV 5대 같은 대규모 실험이 없다.** LLM 프롬프트에 상태를 다 넣는 방식은 규모가 커지면 컨텍스트 한계와 추론 품질 저하에 부딪힌다.

## 8. 우리 연구와의 접점

> [!note] 왜 이 논문을 봤나
> 볼트의 다른 리뷰([[Koopman 다중로봇 최적제어 Part1 - 개념과 정식화]], [[Stackelberg-Koopman 리더-팔로워 궤적 유도]])는 **최적제어·게임이론으로 다중로봇을 조율**하는 계열이다. 이 논문은 같은 문제를 **완전히 다른 층위(LLM 심볼릭 플래닝)** 에서 푼다.

| 관점 | Koopman/게임이론 계열 | **AquaChat++ (LLM 계열)** |
|---|---|---|
| 조율 수단 | 수학적 최적화 (LP, OCP) | **자연어 → 심볼릭 계획** |
| 보장 | 최적성·수렴성 증명 가능 | **보장 없음** (성공률 80~100 %) |
| 다루는 층 | 궤적·제어 수준 | **임무·작업 배분 수준** |
| 제약 처리 | 최적화 제약식 | 프롬프트 + 검증 모듈 |
| 유연성 | 문제를 다시 정식화해야 함 | **말만 바꾸면 됨** |

두 접근은 경쟁 관계가 아니라 **층이 다르다**. 실제로 이 논문의 아래층(RRT* + PID)은 매우 고전적이고, 여기에 Koopman 기반 최적제어를 끼워 넣는 건 자연스러운 조합이다.

**우리 쪽에 직접 쓸 만한 것:**
- **BlueROV2 6-DOF 파라미터 표**(Table 1)와 **추력 배분 행렬 $K$**(식 10) — UUV Simulator 검증값이라 시뮬레이션에 그대로 인용 가능. [[BlueROV2 구매리스트]] 관련 실기체와도 대응된다.
- **열화 계수 $d$를 넣은 제약 최적화 추력 배분** — 구현이 간단하고 효과가 명확하다.
- **나선 궤적 파라미터화**(식 6) — 원통 구조물 검사의 표준 패턴.
- **yaw 붕괴 사례** — 과구동 시스템에서 자유도별 우선순위를 두지 않으면 어떻게 되는지 보여주는 좋은 반례.

## 9. 한 줄 총평

**"LLM이 다중 수중로봇 임무 계획에 쓸 만한가"에 대해 처음으로 구체적인 수치를 제시한 논문.** 답은 **"조건부로 그렇다"** — 원샷 LLM(CLP)은 제약 조건 앞에서 완전히 무너지고, 반복 협상 구조(MAS)를 씌워야 80~100 %가 나온다. 다만 **외부 베이스라인 없이 LLM끼리만 비교했고 전부 시뮬레이션**이라, "LLM이 기존 방법보다 낫다"는 아직 증명되지 않았다. 가장 값진 부분은 오히려 **F2,4,5에서 위치는 멀쩡한데 yaw가 무너져 검사가 불가능해지는** 결과 — 임무 목적이 제어 목표를 결정해야 한다는 걸 숫자로 보여준다.
