# 멀티프로세싱과 생산자-소비자 패턴 (Multiprocessing & Producer-Consumer)

> [!abstract] 한 줄 요약
> **멀티프로세싱(multiprocessing)**은 하나의 프로그램을 여러 개의 독립된 "프로세스(별도의 실행 흐름)"로 쪼개 **동시에** 돌리는 방법이다. **생산자-소비자 패턴**은 한쪽(생산자)이 데이터를 계속 만들어 큐(대기줄)에 넣고, 다른 쪽(소비자)이 큐에서 꺼내 쓰는 협업 구조로, 서로 속도가 달라도 큐가 완충 역할을 해준다.

> [!note] 왜 "프로세스"인가? — 파이썬의 특수 사정
> 파이썬은 **GIL(Global Interpreter Lock)**이라는 잠금장치 때문에, 같은 프로그램 안의 여러 "스레드(thread)"를 써도 CPU 코드가 진짜 동시에 실행되지 않는다(한 번에 하나씩만). 이를 피하려면 아예 **별도의 프로세스**(독립된 메모리 공간을 가진, 운영체제가 보는 진짜 별개의 프로그램)를 여러 개 띄워야 진짜 병렬 실행이 된다. 이것이 `multiprocessing` 모듈이 필요한 이유다.

## 1. 비유 — 공장의 두 부서

**생산 부서(생산자, producer)**가 부품을 계속 만들어 **컨베이어 벨트(큐, queue)** 위에 올려놓는다. **조립 부서(소비자, consumer)**는 벨트에서 부품을 하나씩 집어 조립한다.

- 생산 부서와 조립 부서는 **서로 다른 건물**(=별도의 프로세스)에 있어서 서로의 내부 사정을 모른다. 오직 벨트를 통해서만 소통한다.
- 생산 속도와 조립 속도가 정확히 같을 필요가 없다. 벨트(큐)가 잠깐의 속도 차이를 흡수해준다.
- 벨트가 꽉 차면 생산 부서는 잠깐 멈추고(back-pressure), 벨트가 비면 조립 부서가 기다린다.

이 챕터의 "재생 버퍼 학습을 여러 프로세스로 쪼개기"가 정확히 이 구조다: **"플레이 프로세스"(생산자)** 는 환경과 상호작용해서 경험(experience)을 만들어 큐에 넣고, **"학습 프로세스"(소비자)** 는 큐에서 경험을 꺼내 재생 버퍼에 쌓고 신경망을 학습시킨다.

## 2. `torch.multiprocessing` — 표준 라이브러리의 PyTorch 버전

파이썬 표준 라이브러리에 이미 `multiprocessing` 모듈이 있다. PyTorch는 이를 거의 그대로 감싼(래핑한) `torch.multiprocessing`을 제공하는데, 왜 굳이 별도 버전을 쓸까?

> [!important] 핵심 이유 — 텐서를 복사 없이 공유
> 보통 여러 프로세스는 **메모리를 공유하지 않는다**(비유: 서로 다른 건물). 그래서 한 프로세스의 데이터를 다른 프로세스로 보내려면 원래는 **직렬화(serialize) → 전송 → 역직렬화**라는, 데이터를 통째로 복사하는 과정이 필요하다. `torch.multiprocessing`은 텐서에 대해 **공유 메모리(CPU 텐서)** 또는 **CUDA 참조(GPU 텐서)** 방식을 써서, 이 복사 과정 없이 프로세스 간에 텐서를 빠르게 넘길 수 있게 해준다. (GPU/CUDA 배경은 [[GPU와 CUDA]] 참고)

```python
import torch.multiprocessing as mp
```

임포트 한 줄만 바꾸면 이후 `mp.Queue`, `mp.Process` 등 표준 `multiprocessing`과 똑같은 API를 그대로 쓸 수 있다.

## 3. 핵심 도구 두 가지

### `mp.Process` — 별도의 실행 흐름

```python
play_proc = mp.Process(target=play_func, args=proc_args)
play_proc.start()
```

- `target`: 새 프로세스가 실행할 함수.
- `args`: 그 함수에 넘길 인자들.
- `.start()`: 실제로 새 프로세스를 띄워서 `target` 함수를 실행하기 시작한다. 메인 프로세스는 이 호출 직후 곧바로 다음 줄로 넘어간다(기다리지 않음) — 즉 **두 프로세스가 이제부터 동시에 돈다.**

### `mp.Queue` — 프로세스 간 우편함

```python
exp_queue = mp.Queue(maxsize=2)
```

- 여러 프로세스가 안전하게 데이터를 주고받을 수 있는 **스레드/프로세스 안전(thread/process-safe) 대기열**이다. 한쪽이 `.put(item)`으로 넣으면 다른 쪽이 `.get()`으로 꺼낸다.
- `maxsize=2`: 큐에 최대 2개까지만 쌓아둘 수 있다. 이보다 많이 쌓이면 생산자의 `.put()`이 **자리가 빌 때까지 대기**한다. 이것이 바로 위에서 말한 "벨트가 꽉 차면 생산 부서가 멈춘다"는 완충 장치다. 무한정 쌓이게 두면 메모리가 끝없이 늘어날 수 있으므로 크기를 제한하는 것이 안전하다.

## 4. `mp.set_start_method('spawn')`

```python
if __name__ == "__main__":
    mp.set_start_method('spawn')
```

새 프로세스를 만드는 방식은 여러 가지가 있는데(`fork`, `spawn`, `forkserver`), `spawn`은 **완전히 새로운 파이썬 인터프리터를 처음부터 새로 띄우는** 방식이다. 다소 느리지만, 운영체제나 GPU(CUDA) 환경에 상관없이 가장 안정적으로 동작해서 "가장 유연한" 방법으로 권장된다. `if __name__ == "__main__":` 안에서 호출하는 이유는, 새로 스폰된 프로세스가 같은 파일을 다시 임포트할 때 이 설정 코드가 무한히 반복 실행되는 것을 막기 위해서다.

## 5. 이 챕터에서 왜 유용한가?

RL 학습은 원래 "행동 선택 → 환경과 상호작용 → 재생 버퍼에 저장 → 버퍼에서 샘플링 → 신경망 학습"을 반복한다. 이 중 **앞부분(환경과 노는 것)**과 **뒷부분(신경망 학습)**은 서로 독립적으로 돌 수 있는 작업이다. 특히 환경 시뮬레이션 자체가 무겁고 느린 경우(예: 물리 시뮬레이터), 이 둘을 별도 프로세스로 쪼개면 한쪽이 노는 동안 다른 쪽도 쉬지 않고 계속 일할 수 있어 전체 속도가 빨라진다.

## 세 줄 정리
- 파이썬은 GIL 때문에 진짜 병렬 실행을 하려면 스레드가 아니라 **별도 프로세스**가 필요하다
- `torch.multiprocessing`은 텐서를 복사 없이 프로세스 간에 공유할 수 있게 해주는 PyTorch 버전 멀티프로세싱 모듈이다
- `mp.Process`로 별도 실행 흐름을 만들고, `mp.Queue`로 생산자(플레이)와 소비자(학습) 프로세스가 안전하게 데이터를 주고받는다
