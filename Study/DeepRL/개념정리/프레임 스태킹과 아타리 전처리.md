# 프레임 스태킹과 아타리 전처리

> [!abstract] 한 줄 요약
> 화면 한 장(정지 이미지)만 봐서는 공이 어느 방향으로 움직이는지 알 수 없다. **프레임 스태킹**은 최근 몇 장의 화면을 겹쳐서 하나의 입력으로 만들어, 신경망이 "속도와 방향"까지 알 수 있게 해준다. 여기에 흑백화·크기 축소 등 여러 전처리를 [[Wrapper 래퍼 패턴]]으로 조합해 학습을 빠르고 안정적으로 만든다.

## 1. 왜 한 장의 사진으로는 부족할까

[[상태 관측 에피소드 정책]]에서 배운 **마르코프 성질**을 떠올려 보자: "현재 상태만 보면 미래를 예측하는 데 충분해야 한다." 그런데 Pong 화면을 딱 한 장만 보면 어떨까?

> [!warning] 정지 사진 문제
> 공이 화면 중앙에 있는 사진 한 장만 보고 "공이 왼쪽으로 가는 중인지, 오른쪽으로 가는 중인지" 맞힐 수 있는가? 불가능하다. 위치는 알아도 **속도와 방향** 정보가 없기 때문이다. 이는 마르코프 성질을 위반하는 상황이라 **부분관측 MDP(POMDP)** 라고 부른다 — 관측(한 장의 화면)이 진짜 상태(공의 위치+속도+방향)를 온전히 담지 못하는 것이다.

## 2. 해결책 — 여러 장을 겹쳐서 보기

> [!tip] 비유 — 만화책의 여러 컷
> 만화책에서 공이 날아가는 장면을 그릴 때, 한 컷만 보여주면 정지된 공처럼 보인다. 하지만 **연속된 서너 컷**을 나란히 놓고 보면, 공의 잔상이 이어지면서 "아, 오른쪽 아래로 빠르게 날아가고 있구나"를 바로 알 수 있다. 프레임 스태킹은 정확히 이 원리다 — 최근 4개의 화면을 겹쳐 하나의 입력(4채널 이미지)으로 만든다.

이 챕터에서는 보통 **k=4**개의 연속된 프레임을 쌓는다. 이렇게 하면 입력 텐서의 모양이 (4, 84, 84)가 되어, 앞서 배운 [[합성곱 신경망 CNN]]의 첫 번째 합성곱층 `input_shape[0]`(채널 수)로 그대로 들어간다.

> [!note] 이것도 결국 하나의 '하드코딩된 요령'이다
> 저자도 이 방법이 완벽하지 않다고 인정한다 — 4프레임보다 더 긴 의존성(예: 아주 느리게 움직이는 물체)이 있는 게임에서는 부족할 수 있다. 그래도 대부분의 아타리 게임에서는 잘 작동하는 실용적인 타협안이다.

## 3. 그 밖의 전처리 래퍼들

책은 [[Wrapper 래퍼 패턴]]을 이용해 여러 전처리를 체인처럼 연결한다. 각각의 역할을 표로 정리하면 다음과 같다.

| 래퍼 | 하는 일 | 왜 필요한가 |
|---|---|---|
| `FireResetEnv` | 게임 시작 시 자동으로 FIRE(발사) 버튼을 누름 | 일부 게임(Pong 포함)은 FIRE를 눌러야 게임이 시작되는데, 안 누르면 화면이 멈춘 채라 이 역시 관측만으로는 알 수 없는 POMDP가 됨 |
| `NoopResetEnv` | 시작할 때 무작위 횟수(최대 30번)만큼 아무 행동도 안 함 | 매번 완전히 똑같은 상태로 시작하지 않도록 다양성을 줌(인트로 화면 건너뛰기 겸용) |
| `MaxAndSkipEnv` | K(보통 4)스텝마다 한 번만 행동을 결정하고, 그 행동을 반복 적용. 마지막 두 프레임의 픽셀별 최댓값을 관측으로 사용 | 매 프레임 신경망을 돌리는 건 비용이 크고, 연속 프레임 차이가 작아 굳이 필요 없음. 최댓값을 쓰는 이유는 아타리 특유의 "깜빡임(flickering)" 현상(스프라이트 수 제한으로 물체가 격프레임으로만 그려짐) 때문 |
| `WarpFrame` | 210×160 컬러 화면을 흑백 84×84로 축소 | 데이터 크기를 크게 줄여 메모리·연산량 절약. 색상 정보는 대개 게임 진행에 불필요 |
| `BufferWrapper` | 최근 n_steps(보통 4)개의 관측을 쌓아 하나로 합침 | 앞서 설명한 프레임 스태킹 — 속도·방향 정보 제공 |
| `ImageToPyTorch` | 이미지 축 순서를 (높이, 너비, 채널)에서 (채널, 높이, 너비)로 변경 | PyTorch의 `Conv2d` 층은 채널이 맨 앞에 와야 함 |
| `ClipRewardEnv` | 보상을 -1, 0, 1로 자름 | 게임마다 점수 스케일이 천차만별(Pong은 ±1, KungFuMaster는 +100)이라 그대로 쓰면 손실 함수 스케일이 게임마다 달라져 공통 하이퍼파라미터를 쓰기 어려움 |

## 4. 왜 이렇게까지 신경 써야 할까

저자는 "DQN이 수렴하지 않을 때, 원인이 코드가 아니라 **환경 래핑을 잘못한 것**인 경우가 많다"고 경고한다. 실제로 FIRE 버튼을 누르는 `FireResetEnv`를 빠뜨려 며칠을 디버깅한 경험을 언급할 정도다. 즉 전처리 래퍼들은 "성능을 조금 높이는 팁"이 아니라, **환경을 마르코프 성질에 맞게 만들어 학습이 아예 가능하게 하는 전제조건**에 가깝다.

## 세 줄 정리
- 화면 한 장만으로는 속도·방향을 알 수 없어 마르코프 성질이 깨진다(POMDP).
- 최근 4프레임을 겹치는 **프레임 스태킹**으로 이 정보를 보완한다.
- FIRE 자동 입력, 프레임 스킵, 흑백 축소, 보상 클리핑 등 여러 래퍼를 체인으로 연결해 학습을 안정화·경량화한다.
